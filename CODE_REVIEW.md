# Проверка ChessZone — 2 ноября 2026

Проверена версия `311225cca810c37779342b0b0e3704a5a2c2a7ef`, включая `92eb99d`, `0677b01` и `6577b95`. Все пять сценариев ниже воспроизведены на исходном сервере локально и исправлены в этой сборке. Ссылки относятся к исходным строкам, до исправлений.

## 1. P1 — некорректный тип данных завершает сервер

[server.js:36–39](https://github.com/eNtry111/chesszone-online/blob/311225cca810c37779342b0b0e3704a5a2c2a7ef/server.js#L36-L39), вызов [514–518](https://github.com/eNtry111/chesszone-online/blob/311225cca810c37779342b0b0e3704a5a2c2a7ef/server.js#L514-L518).

Событие регистрации с объектом вместо имени, содержащим `toString: null`, вызывает необработанное исключение `String(value)`. Локальный процесс завершился с кодом 1. При хранении в памяти это обрывает все партии. Похожие преобразования были у кода комнаты, ID приглашения, чата и числовых настроек. Проблема преобразования имени существовала и до приглашений в `cleanName`; новая регистрация добавила путь без создания комнаты.

Исправление: проверять типы до обработки, отклонять объекты вместо строк и проверять числовые настройки по допустимым значениям без преобразования. Тест подтверждает, что сервер принимает нормальный ход после всех некорректных запросов.

## 2. P1 — правильный токен не гарантирует переподключение

[server.js:535–544](https://github.com/eNtry111/chesszone-online/blob/311225cca810c37779342b0b0e3704a5a2c2a7ef/server.js#L535-L544), проверка ника [48–50](https://github.com/eNtry111/chesszone-online/blob/311225cca810c37779342b0b0e3704a5a2c2a7ef/server.js#L48-L50).

Открытие комнаты во второй вкладке с верным токеном отклоняется: ник ещё принадлежит первой вкладке. Аналогично блокируется возврат, если после обрыва временный ник занял другой посетитель.

Исправление: восстанавливать место по токену независимо от временного ника. Перенос своей активной сессии освобождает её ник; чужой занятый ник не отбирается. Старая вкладка возвращается в меню, чтобы не перехватывать комнату при следующем переподключении. Оба случая проверены тестами.

## 3. P2 — пропадает взятие на проходе при включении свободного режима

[server.js:672–678](https://github.com/eNtry111/chesszone-online/blob/311225cca810c37779342b0b0e3704a5a2c2a7ef/server.js#L672-L678).

В chess.js 1.4.0 обычный `fen()` скрывает поле en passant, когда это взятие раскрывает шах своему королю. При включении свободного режима поле всё ещё нужно.

Воспроизведение: `4k3/8/8/8/4p3/8/3P4/K3R3 w - - 0 1`, ход `d2-d4`, включение свободы. Чёрная пешка связана по линии e; обычный FEN даёт `-`, поэтому разрешённое в свободном режиме `e4-d3` ошибочно отклоняется.

Исправление: переносить позицию через `game.fen({ forceEnpassantSquare: true })`. Проверены фактическое взятие и удаление пешки с d4.

## 4. P2 — приглашение остаётся после создания адресатом своей комнаты

[server.js:550–577](https://github.com/eNtry111/chesszone-online/blob/311225cca810c37779342b0b0e3704a5a2c2a7ef/server.js#L550-L577).

A приглашает B; до ответа B отправляет собственное приглашение C. Сервер создавал B комнату, но оставлял A → B. Окно у B уже закрыто, A ждёт до 45 секунд.

Исправление: перед автоматическим созданием комнаты вызвать `cancelInvitesFor(socket.id)`. A сразу получает уведомление; старый ID больше не принимается.

## 5. P2 — одно соединение занимает оба цвета

[server.js:534–544](https://github.com/eNtry111/chesszone-online/blob/311225cca810c37779342b0b0e3704a5a2c2a7ef/server.js#L534-L544), назначение [485–487](https://github.com/eNtry111/chesszone-online/blob/311225cca810c37779342b0b0e3704a5a2c2a7ef/server.js#L485-L487).

Создатель повторно отправляет `join-room` в свою незаполненную комнату без токена. Сервер выделял чёрное место, оставляя тот же socketId у белых. Клиент и сервер по-разному определяют цвет, оба места заняты, нормальная партия невозможна. Этот дефект есть и в `837b431`, то есть он не внесён последними коммитами.

Исправление: уже подключённому участнику повторный вход возвращает существующее место, не выделяя новое.

## Результаты партий и границы проверки

Правило одинокого короля соответствует README и намеренно отличается от официальных шахмат. Проверены победа белых и чёрных, ничья при двух королях, блокировка последующих ходов и оба режима. Если король съеден в свободном режиме, это правило намеренно не применяется. Если очередной стороне нечем ходить, потребуется сброс режима владельцем.

Дополнительно проверены защита приглашения от чужого ответа и повторного использования, занятость игрока, закрытая одиночная комната, запоздалые ответы движка, сложность, реванш, переподключение, сбой движка и повторный запуск. В тестах гонок ответы ИИ управляются тестом; отдельная команда `npm run test:stockfish` запускает настоящий движок на Skill 2, 8 и 18.

Это проверка перечисленных сценариев и изменённых участков, не гарантия отсутствия любых ошибок и не полный аудит хостинга.
